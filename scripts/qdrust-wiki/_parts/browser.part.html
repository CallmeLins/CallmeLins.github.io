浏览器插件（无头浏览器签到）

纯 HTTP 做不了的那一步，用 api://browser/* 补齐：签名、验证码、JS 渲染与多步表单交互。

设计取舍

浏览器插件是可选的补充，不是主流程。推荐的用法是「混合签到」：只有真正需要浏览器的一步走 api://browser/*，其余步骤仍走普通 HTTP 请求。这样既保留了 HAR 的轻量，又不必为一个签名步骤引入整套爬虫框架。

启用方式（三步）

  1. 准备一个无头浏览器端点（见下方「端点后端三选一」）。
  2. 给服务设置 QDRUST_BROWSER_URL（Docker 部署写在 compose.yaml 的 environment 里）。
  3. 重启服务。之后模板里就能直接用 api://browser/*，无需在 WebUI 插件管理页新建条目。
services:
  qdrust:
    # ...
    environment:
      QDRUST_BROWSER_URL: ws://browserless:3000
  browserless:
    image: ghcr.io/browserless/chromium:latest
    environment:
      TOKEN: change-me
      CONCURRENT: 5
    restart: unless-stopped

浏览器客户端代码已编译进 server 二进制，不再需要单独的 qdrust-plugin-browser 子进程或 QDRUST_BROWSER_PLUGIN_BIN 配置。

Action 一览

Action 分为一次性与会话两类：

Action类型用途参数返回体
start会话 开一个标签页并导航到 url，返回可复用的会话 id url 必填 {"session": "<id>"}
end会话 关闭会话并释放标签页 session 必填 {"session": ..., "status": "closed"}
keepalive会话 刷新会话空闲 TTL（长时间等待人工输入时保活） session 必填 {"ok": true, "session": ...}
type会话 在 selector 元素上输入 value（原生键盘事件，兼容 SPA）；clear=1 先清空，submit=1 输入后按回车 session、selector、value 必填；可选 clear、submit {"ok": true, "session": ..., "selector": ...}
click会话 点击 selector 元素；可选 wait=<ms> 点击后等待、wait_selector=<css> 轮询等某元素出现（最长 15s） session、selector 必填；可选 wait、wait_selector {"ok": true, "session": ..., "selector": ...}
content一次性 渲染后取页面 HTML（JS 已执行，适合 SPA / 动态加载） url 必填 页面 HTML 文本
eval一次性 在页面里执行 JS，取 token / 签名 / cookie / 页面状态 url、expr 必填 求值结果的 JSON
screenshot一次性 截图（过验证码给人看 / 留档） url 必填；可选 full_page=1、format=png|jpeg、width/height、wait=<ms> {"mimeType": ..., "data": <base64>}

判定规则：content / eval / screenshot 若带 session 参数则在指定会话页上执行，否则开一张一次性标签页（用完即关）；type / click 必须带 session。

端点后端三选一

  • Browserless 自托管：ws://localhost:3000——推荐，compose.yaml 里已备好注释掉的 browserless 服务。
  • 本地 Chromium / obscura：http://localhost:9222，即带 --remote-debugging-port=9222 启动的 Chrome。
  • Browserless 云端：wss://chrome.browserless.io?token=...。

混合签到：模板怎么写

核心思路：普通 HTTP 步骤用 HAR 原样请求；需要浏览器的一步插入 api://browser/*，把它的返回体用 extract_variables 提取成变量，供后续 HAR 步骤用 {{var}} 填充。

一次性用法

例 1：eval 取签名 / token，回填到后续 HTTP 请求

{
  "entries": [
    {
      // 浏览器步骤：登录页里执行 JS 取签名
      "request": { "method": "GET", "url": "api://browser/eval?url=https://example.com/signin&expr=window.__sig()" },
      "extract_variables": [
        { "name": "sig", "re": "\"([a-zA-Z0-9_-]+)\"", "from": "content" }
      ]
    },
    {
      // 真正的签到请求：把签名回填进 body
      "request": {
        "method": "POST",
        "url": "https://example.com/api/checkin",
        "postData": { "mimeType": "application/json", "text": "{\"sig\":\"{{sig}}\"}" }
      }
    }
  ]
}
正则要带上引号

extract_variables 的 re 是对整个返回体文本做正则匹配。eval 返回的是 JSON（字符串值带引号），所以取字符串时要转义引号："([a-zA-Z0-9_-]+)"；数字 / 布尔值则不带引号。

例 2：content 抓渲染后的页面，正则提取变量

SPA 页面内容由 JS 动态生成，普通 HTTP 拿到的只是空壳。用 content 拿渲染后的 HTML 再提取：

{
  "request": { "method": "GET", "url": "api://browser/content?url=https://example.com/dashboard" },
  "extract_variables": [
    { "name": "nickname", "re": "nickname[^>]*>([^<]+)<", "from": "content" }
  ]
}

例 3：screenshot 过验证码 / 留档

截图把当前页面状态打给人看（data 为 base64）。适合无法自动破解的验证码场景——人工看图后把答案填进下一步变量，或单纯用于失败时留档排查：

{
  "request": {
    "method": "GET",
    "url": "api://browser/screenshot?url=https://example.com/captcha&wait=2000&format=png"
  },
  "extract_variables": [
    { "name": "captcha_img", "re": "\"data\":\"([A-Za-z0-9+/=]+)\"", "from": "content" }
  ]
}

会话用法：多步页面交互 / 人工过验证码

对于「登录后拿 cookie 再签到」这类需要在同一页面上连续操作的流程，用 start 开一个会话，跨多个步骤对同一 session 做 type / click / content。会话在多次独立调用间保持存活，因此天然支持中间等人——比如让人工过完验证码再继续。 

{
  "entries": [
    {
      // 1. 开会话进登录页，把 session id 存进变量
      "request": { "method": "GET", "url": "api://browser/start?url=https://example.com/login" },
      "extract_variables": [ { "name": "sess", "re": "\"session\":\"([0-9a-f]+)\"", "from": "content" } ]
    },
    {
      // 2. 往 #user 输入账号
      "request": { "method": "GET", "url": "api://browser/type?session={{sess}}&selector=%23user&value=my_account" }
    },
    {
      // 3. 往 #pass 输入密码，submit=1 回车提交（触发登录跳转）
      "request": { "method": "GET", "url": "api://browser/type?session={{sess}}&selector=%23pass&value=my_pw&submit=1" }
    },
    {
      // 4. 等 dashboard 出现后抓渲染后 HTML，提取登录态信息
      "request": { "method": "GET", "url": "api://browser/content?session={{sess}}&url=https://example.com/dashboard" },
      "extract_variables": [ { "name": "nickname", "re": "nickname[^>]*>([^<]+)<", "from": "content" } ]
    },
    {
      // 5. 用完关会话
      "request": { "method": "GET", "url": "api://browser/end?session={{sess}}" }
    }
  ]
}
两个最容易踩的坑

① 用 # 选择器时务必做 URL 编码（#user → %23user），否则 # 会被当作片段标识符，把 query 整个截掉。
② 会话 id 要由第一步的 extract_variables 提出并存进变量，后续步骤才能用 {{sess}} 复用。

会话生命周期与回收

  • 存活位置：会话存于 server 内存，由 QDRUST_BROWSER_URL 配置的服务进程全局持有，每会话一个标签页。进程重启即全部清空，向导需要重新 start。
  • 空闲回收：闲置超过 30 分钟被后台任务回收；无论是否活跃，最长存活 24 小时。
  • 并发上限：16 个并发会话。
  • 建议：向导式流程结束后显式 end 释放标签页；被遗忘的会话由上述回收规则兜底，不会泄漏。

需要「人等验证码」的流程，可在人工环节前后用 keepalive（或直接让页面停留）刷新会话空闲 TTL，避免会话被 30 分钟空闲回收提前清掉。

行为与限制

  • 错误处理：未配置 QDRUST_BROWSER_URL、连接失败、找不到元素或会话、参数缺失等都会返回 502 信封，可用 success_asserts / failed_asserts 感知——不会静默降级，也不会中断整个任务。
  • 连接复用：未带 session 的 content / eval / screenshot 也复用同一条长连接（只是标签页用完即关），免去每次冷启动的握手开销。
  • 选择器找不到：type / click 找不到目标元素返回 502；click 的 wait_selector 最长轮询 15 秒。
  • 没有 clear()：想清空输入框用 type 的 clear=1（内部是 Ctrl+A + Backspace）。
  • 同会话串行：同一会话的并发操作按顺序执行，避免两次按键交叠；跨会话可并行。
