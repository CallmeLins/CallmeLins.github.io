使用指南

从初始化管理员到跑起第一个任务：配置 OIDC / 反向代理 Header 第三方登录、导入旧 QD 模板、创建任务与填写变量、可视化编辑 HAR、配置调度与随机延迟、cron 时区与夏令时、查看运行日志，以及命令行工具。

首次启动与管理员

  1. 启动服务后访问 http://localhost:8923/（或你配置的域名 / 二级目录）。
  2. 首次打开会引导创建初始管理员账号；之后其他用户走开放注册流程。
  3. 管理员可在「设置 / 管理员」中管理用户、站点设置、日志清理、备份与恢复。

还没部署？先看部署与运维。

第三方登录（OIDC / 反向代理 Header）

自托管部署可选择通过外部身份提供方（IdP）登录，本地账号密码能力始终保留。

认证模式与开关

默认 local，严格后向兼容：

  • QDRUST_AUTH_MODE：local | hybrid | oidc。 oidc 模式下本地登录入口默认关闭；若想保留一个本地管理员应急入口，同时设 QDRUST_LOCAL_LOGIN_ENABLED=true。
  • 外部提供方通过独立开关叠加：QDRUST_OIDC_ENABLED / QDRUST_HEADER_AUTH_ENABLED。

WebUI 登录页按 GET /api/v1/auth/config 返回的策略渲染入口，详见API 接口 · 认证与会话。

OIDC（Authorization Code + PKCE）

对接 authentik / authelia / keycloak / pocket-id：

QDRUST_AUTH_MODE=hybrid          # 或 oidc（纯 IdP，关本地入口）
QDRUST_OIDC_ENABLED=true
QDRUST_OIDC_PROVIDER_NAME=Authentik   # SSO 按钮上显示的名称（来自显式配置）
QDRUST_OIDC_ISSUER=https://auth.example.com/application/o/qdrust/
QDRUST_OIDC_CLIENT_ID=qdrust
QDRUST_OIDC_CLIENT_SECRET=...
# QDRUST_OIDC_REDIRECT_URI 留空则由服务端在请求时按反代前缀推导
QDRUST_OIDC_SCOPES="openid profile email"
QDRUST_OIDC_AUTO_CREATE_USERS=true    # 首登自动建档（哨兵口令，本地无法登录该外部账号）
QDRUST_OIDC_DEFAULT_ROLE=user         # 未命中 admin 组的建档角色
QDRUST_OIDC_ADMIN_GROUPS=qdrust-admins # 命中则首次建档为 admin
QDRUST_OIDC_GROUPS_CLAIM=groups       # ID token 中携带组成员身份的 claim 名（默认 groups）
# --- 可选：OIDC 单点登出（end-session） ---
# QDRUST_OIDC_LOGOUT_URL=https://auth.example.com/protocol/openid-connect/logout
#   # 用户点击登出时，清本地会话后顶层跳转到该 IdP 端点，把提供方会话也一并结束。
# QDRUST_OIDC_POST_LOGOUT_REDIRECT_URI=https://your.domain/qd/
#   # 可选：IdP 登出后跳回的应用地址。仅在 IdP 侧已登记该地址时才应配置，
#   # 否则多数 IdP 会拒绝未登记的回跳参数，用户将停留在 IdP 自带的登出完成页。

在 IdP 侧把回调地址登记为 https://你的域名[/<base_path>]/api/v1/auth/oidc/callback。

纯 OIDC 模式的登录体验

QDRUST_AUTH_MODE=oidc 时，未登录用户访问页面会自动跳转到 IdP 发起 SSO， 不再先停留在一个多余的登录面板；仅在回调失败（带 login_error）或已登录时保留 SSO 兜底面板， 避免重定向循环。

角色映射（groups claim）

OIDC 首登按 ID token 里的 groups claim（可通过 QDRUST_OIDC_GROUPS_CLAIM 换成 IdP 实际使用的 claim 名，如某些 Keycloak 映射后的 roles）解析角色：claim 命中 QDRUST_OIDC_ADMIN_GROUPS 中任一成员则建档为 admin，否则落 QDRUST_OIDC_DEFAULT_ROLE。若 IdP 不在 ID token 内下发组（部分 IdP 只在 userinfo 返回）， 则保持 claim 缺失、统一落 default_role，再让管理员手动调整。

首登用户名的取值链

按 preferred_username → nickname → name → email 本地部分依次取第一个可读值。这里会跳过明显是不透明标识的候选 （如全十六进制 / UUID / 纯数字的 preferred_username——部分 IdP 把内部 id 直接塞进该 claim）， 避免把一串 hex 存成登录名，此时只要 name/email 可读就会取到它们。

ID token 只给 sub 时的 UserInfo 回退

少数 IdP（部分 authentik / Keycloak 配置、企业 IdP）签发的 ID token 只含 sub， 把 preferred_username/name/email 全部放在 UserInfo 端点。 此时 qdrust 会用换来的 access_token 调 userinfo_endpoint 补取这些 claim，再走上面的取值链， 从而拿到可读用户名而不是那串 sub id。

该调用是尽力而为：provider 未公布 userinfo、或调用失败，都只记日志、不阻断已验签的登录。

最终兜底（整条链全空时）

若 ID token 与 UserInfo 都没给出任何可读字段（IdP 只发一个不透明 sub），qdrust 不再把原始 sub 当用户名，而是从中派生一个短且稳定的可读句柄 user-<前 8 位> （如 user-23cc07f8；派生前会去掉 uuid 连字符等分隔符，同一 sub 恒定映射）。 sub 本身仍单独存储，作为账号的稳定身份键。

想彻底避免出现兜底名，可在 IdP 侧给 ID token 补上 preferred_username/name 的 mapper（或确保 profile/email scope 生效）。只影响新建档， 存量用户需手动改名或重新建档。

二级目录部署下的 SSO 登录

登录判定不再依赖 /ready 探针（后端把 /ready//health 保留在根路径供 Docker HEALTHCHECK；经原样转发的 nginx 时，二级目录页面发起的根路径探针本就不会命中）。 会话有效性改为以 /session 成功为准，因此子路径部署时 SSO 登录不再被探针失败误判为「未登录」。

反向代理 Header 认证（forward-auth）

对接 nginx auth_request / authelia forward-auth / authentik proxy：反代在每个请求注入身份头， 服务端仅在源 IP 属于可信代理时才信任： 

QDRUST_HEADER_AUTH_ENABLED=true
QDRUST_HEADER_TRUSTED_PROXIES=127.0.0.1,10.0.0.1   # 必须显式配置
QDRUST_HEADER_TRUSTED_PROXY_REQUIRED=true           # 默认 true：无可信代理则拒绝启动
QDRUST_HEADER_USER_HEADER=Remote-User
QDRUST_HEADER_EMAIL_HEADER=Remote-Email
QDRUST_HEADER_GROUPS_HEADER=Remote-Groups
QDRUST_HEADER_GROUPS_SEPARATOR=,
QDRUST_HEADER_AUTO_CREATE_USERS=false               # 默认 false：仅已建档用户可登录
QDRUST_HEADER_DEFAULT_ROLE=user
QDRUST_HEADER_ADMIN_GROUPS=qdrust-admins

Header 认证不每次建会话：仅当无有效会话、或头身份与会话用户不一致时才会建/刷新 （身份漂移会撤销旧会话）。登出只清除 qdrust 自身会话。被隔离到 /api/v1/auth/* 之外的 普通 API 与 SPA 均由该中间件兜底。

反代需放行真实源 IP（Header 认证要读 ConnectInfo 源地址）。示例 nginx——在 location / 里把已认证的用户身份注入并转发给 8923：

location / {
    proxy_pass http://127.0.0.1:8923;
    proxy_set_header Host $host;
    # authelia/authentik 校验通过后注入；务必去掉客户端可能伪造的同名头
    proxy_set_header Remote-User   $remote_user;     # 或取自 auth_request 变量
    proxy_set_header Remote-Email  $upstream_http_remote_email;
    proxy_set_header Remote-Groups $upstream_http_remote_groups;
}
角色在首次建档时写死

Header 与 OIDC 两种外部认证的 groups → admin 角色都在首次建档时写死， 后续组变化不会自动升/降权，需管理员显式调整。OIDC 从 ID token 的 groups claim（可配置）取组； 若 IdP 不把组放进 ID token（仅在 userinfo），该 claim 缺失，首登统一落 default_role。 组到角色的精细实时同步留待后续按需扩展。

导入 QD HAR 模板

  • 在 WebUI 的模板页点击导入，选择从旧 QD 导出的 *.har.json。
  • 导入时会校验并保留原始 HAR JSON，兼容样本见仓库的 tests/fixtures。
  • 也可以用命令行先校验再导入：
cargo run -p qdrust-cli -- validate .\template.har.json

模板的字段含义与两种形态见模板与表达式 · 旧 QD HAR。

创建与运行任务

  1. 模板必选：新建任务时先选模板——任务的请求完全由模板决定（多页模板常混合 GET/POST）， 任务本身不携带请求方法 / URL / 请求头 / 请求体。
  2. 填写变量（模板需要的变量会按 QD 语义自动列出，见模板变量是怎么算出来的）、配置 cron / 间隔调度。
  3. 用「立即运行」手动触发，或在运行记录中查看每一步的请求 / 响应 / 提取变量；支持取消正在执行的运行。
  4. 模板页提供两种导入来源：从本地导入 QD HAR，或从订阅的模板库里挑——后者是先预览、保存才入库。本站公开模板经 PushRequest 审批后发布。
任务列表里的方法与 URL 只是「镜像」

任务列表里的请求方法与 URL 是模板首条请求的镜像，只用于展示，执行始终以模板为准。 早于该规则的存量任务（未绑定模板、自带一条请求）编辑时仍会保留「（无模板）」选项与其原有请求，不会被改动。

变量、断言与表达式写法见模板与表达式。

可视化 HAR 编辑器

WebUI 提供可视化编辑器，可直接增删改请求、设置请求头 / 表单 / 鉴权、编写 success_asserts 与 extract_variables，无需手改 JSON。

调度与随机延迟

  • 两种调度：固定间隔与 cron，都在可视化调度器中配置。
  • 随机延迟：让同一任务的多次执行在时间上打散，避免被目标站点识别为固定节奏。
  • 变量预填：模板变量支持在创建任务时预填默认值。

时区与夏令时

cron 按每个任务各自的 IANA 时区（timezone 字段）求值，DST 感知：

  • 设 America/New_York 的任务，0 9 * * * 会全年在当地 09:00 触发，无需为冬令 / 夏令手动改 cron。
  • 任务未设 timezone 时，使用服务端 QDRUST_DEFAULT_TIMEZONE（默认 Asia/Shanghai）。
  • WebUI 中任务列表与运行历史的「上次运行 / 开始时间」也按该任务时区展示；未设时区则用查看者浏览器本地时区。

服务端默认时区的设置方式见部署与运维 · 环境变量。

运行日志与历史

  • 每次运行会记录 QD 风格的文本日志。
  • 任务详情页可查看该任务的运行历史，并支持清空历史记录。
  • 活跃运行的步骤通过 WebSocket 实时推送。
  • 已完成记录的保留天数由 LOG_RETENTION_DAYS 控制，0 表示永久保留。

运行日志总览

任务页标题右侧的「运行日志」打开的是一个宽弹窗（不是独立页面），把所有任务的运行放在同一张表里：

  • 按时间倒序，可按「全部 / 成功 / 失败」筛选、按任务过滤，能在行内取消或删除；
  • 点任务名可直接跳到该任务的运行历史；
  • 弹窗底部有它自己的分页条——它是游标分页，只显示「第 N 页」而没有总页数，两个翻页按钮始终可用。每页条数在分页条上设置，不与其他列表互相影响（见下节）。

任务多的时候用它一眼扫完当天所有任务，不必逐个点进任务详情。对应接口 GET /api/v1/runs（status / task_id / limit / before_id 参数，游标分页）。

WebSocket 的端点与消息格式见API 接口 · WebSocket 实时接口。

列表分页与每页条数

任务、订阅、我的模板、公共模板（订阅源汇总）与本站公开模板都按页渲染，默认每页 10 条。

分页条始终显示，不随列表长短收起

分页条在表格下方始终可见——它是修改每页条数的唯一入口。一旦跟着列表长度收起，选到 100 条之后就再也改不回 10 了。只有一页的列表会隐去中间那段翻页控件，只留左边的总条数与右边的条数选择器。

分页条从左到右是三段：

  1. 总条数；
  2. 上一页 / 第 x / y 页 / 下一页（列表只有一页时不显示）；
  3. 每页条数：10 / 20 / 50 / 100。

每个列表各记各的条数，改一个不会动到别的——它们读条数的时机和目的都不一样，共用一份只会让人在改 A 的时候顺手把 B、C 也改了。选择按浏览器存在 localStorage，键是 qdrust.pageSize.<列表名>（tasks / subscriptions / templates / publicTemplates / library / runLog）。它是阅读偏好而不是站点设置，所以不需要服务端状态，也不需要管理员权限。

旧版用一个共享的 qdrust.pageSize；升级时它仍会被读取，作为各列表尚未单独设置过时的起点，但不再被写入。除运行日志外，列表数据本来就整份在浏览器里，改条数只影响渲染、不重新请求；运行日志是服务端分页，改条数会重新取数并把游标重置回第一页（旧游标是按旧条数切的，不能复用）。

筛选与全选

  • 换了筛选条件就回到第 1 页：任务页的搜索 / 分组，模板页的搜索，公共模板库的搜索 / 排序 / 切换来源 / 刷新，以及运行日志的状态 / 任务。
  • 列表变短时页码会自动收回，不会停在已经不存在的页上。
  • 运行日志是游标分页，没有「第几页共几页」可回，所以改筛选或改每页条数时直接清空游标栈重新取数——旧游标是按上一份结果集切的，留着它只会去问「那份列表的下一页」，而那份列表已经不存在了（这正是「按任务筛选好像没生效」的成因：筛选本身是对的，游标替另一份列表答了话）。
  • 「全选」只覆盖当前页（任务与公共模板库两处），免得翻页后看不见的行被批量操作带上。

订阅模板库（汇总与预览）

除了从本地导入 HAR，模板页还可以订阅模板库并从中挑模板：支持官方库 qd-today/templates，以及任何兼容同一规范的第三方库或单个模板文件 URL。 库浏览是模板页内的一块，不是独立页面——没有整页跳转，也就没有「返回模板」这一步。

1. 添加订阅

在「模板」页点标题右侧的「添加订阅」，弹窗里填订阅名称与库地址（例如 https://github.com/qd-today/templates）。

订阅只登记来源，不自动导入

没有「导入方式」的选择：订阅只是登记一个来源目录，不会把模板自动拉进本地——官方库里是几百个模板，全量导入会把你自建的模板淹掉。模板是否导入、何时导入，由你在下方的「公共模板」列表里自己决定。

订阅区域在页面标题下、「我的模板」上方（来源排在它供给的列表之前），行内可随时「编辑 / 启用停用 / 删除」；无订阅时该表格显示为空列表。

2. 浏览汇总

「公共模板」表默认列出所有已启用订阅源的条目（名称、作者、来源、版本、日期、状态），按上游日期倒序，表头可点排序，可搜索名称 / 作者 / 来源。用「订阅源」下拉切到单个来源时，表格多出「订阅源」列，并标出该源是按 tpls_history.json 清单读的还是扫描文件得到的。停用的订阅不进汇总。

3. 导入是预览，不是直接落库

点行内「导入」时，服务端把该条目的上游 HAR 取回来但不落库，编辑器打开的就是它，改好保存才写进「我的模板」——随手点几行不会在模板列表里留下用不上的东西。已导入且无更新的行显示「打开」，直接编辑本地那份、不联网。

  • 已导入的条目标「已导入」；上游版本变新时标「有更新」，点「更新」同样先预览上游那一版，保存后原地更新本地模板（不会生成重名副本），并把来源记录的版本推进到上游版本。
  • 需要一次预载多个时，点工具栏「批量选择」才展开勾选列与批量导入工具条。批量导入是直接的，不逐个预览；汇总视图下勾选可以跨来源，服务端按来源分组调用。入口列会随状态在「导入 / 更新 / 打开」之间切一个主操作。
命名约定：qd-today 语境里的「公共模板」指订阅源的汇总，本页沿用该含义；本站用户互相发布的模板另称「本站公开模板」，默认折叠在页尾。

4. 缓存与读取失败

来源目录有短缓存（90 秒，按仓库 URL 而不是按订阅或账号——同一仓库被两个订阅或两个账号指向时只读一次）。汇总视图一次要读所有来源，而每个来源是两三个 GitHub 请求，所以缓存目录本身；「已导入 / 有更新」不进缓存，每次都由本地库现算，因此刚订阅完立刻就能看到状态变化。工具栏的「刷新」按钮带 refresh，绕过缓存重新读取。

读取失败不会再把来源清空：目录抓取最多试 3 次（间隔 300 / 600 毫秒），只重试传输类失败——连接被断、超时、body 传了一半；HTTP 状态码是上游给的答复（比如仓库没有清单时的 404），重试只会拿到同一个。库抓取的单次请求超时是 60 秒，比其它请求宽：官方清单有 3 MB 且 93% 是内联 HAR，按 API 调用的默认超时收不完 body。缓存过期后重取仍然失败时，会退回用上一份成功读到的目录并标为「缓存」，而不是把该来源变成 0 条——只有你主动点「刷新」时才如实报错，因为那时你问的是「现在是什么样」。

5. 来源的发现规则

与 QD 第三方库规范一致：

  • 仓库根目录有 tpls_history.json 时按其清单读取：har 以模板名为键，值里的 author / comments / version / date / commenturl 就是展示的元数据；HAR 优先取内联的 base64 content，否则按 url、再否则按 filename 下载。
  • 没有清单时回退为扫描仓库树中的 *.har / *.json，此时条目不携带版本，因此不会提示更新。
  • 变量说明（comments）在服务端被规整为纯文本，不注入到页面里。
  • 上游内容有两种形状：标准 HAR（{log:{entries}}）和 QD 导出的请求数组（[{comment, request:{…}, rule:{…}}]）——tpls_history.json 里的 content 就是后者。预览接口按契约原样返回上游文档，所以转成编辑器认得的 HAR 这一步在前端做（与本地文件导入共用同一条转换）；服务端的执行链两种形状都吃得下。

来源记录写在 template_imports（订阅 + 条目名 → 本地模板 + 上游版本），用于判断「已导入 / 有更新」。删除订阅只删除来源记录，已导入的模板会保留（导入是复制到你自己的库，不是软链）。一个读不动的仓库不会让整张表变空：它单独列出错误，其余来源照常显示；条目总数触及上限时列表会说明已被截断。

6. 对应接口

方法路径作用
GET/api/v1/library所有已启用来源的汇总（entries 加上每个来源的 sources 结果与错误），refresh=<bool> 绕过缓存
GET/api/v1/subscriptions/{id}/library单个来源的目录
GET/api/v1/subscriptions/{id}/library/preview取出一条的 HAR 但不落库；条目名走查询参数而不是路径段，因为它是来源自己起的自由字符串，可能含 /
POST/api/v1/subscriptions/{id}/library/apply保存编辑器里的 HAR 并写下来源记录；带 template_id 则原地更新，否则新建
POST/api/v1/subscriptions/{id}/import按名称批量直接导入，逐条返回成功 / 更新 / 失败，并给出写入模板的 id 与是否原地更新

完整参数与权限见API 接口 · 模板订阅与模板库。

命令行（CLI）

校验旧 QD HAR：

cargo run -p qdrust-cli -- validate .\template.har.json

执行 HAR，并传入变量和整体超时：

cargo run -p qdrust-cli -- run .\template.har.json --var token=abc --timeout 60
CLI 的网络策略更严格

CLI 默认拒绝私网、localhost 和无效 TLS 证书，不继承旧 QD 的宽松网络策略。用它调试本地服务时会因此需要额外放行。
