模板与表达式

HAR 兼容契约、Template Schema v1、变量与断言、Jinja2 函数与过滤器、Python 写法的兼容、正则与编码的 Python 读法，以及 api://util/* 内置工具。

两种模板形态

qdrust 里「模板」有两种来源，它们共享同一套执行引擎，但形态不同：

  • 旧 QD HAR——从 QD 导出的 *.har.json，核心兼容契约，导入时校验并保留原始 HAR JSON。绝大多数已有资产走这条路。
  • Template Schema v1——qdrust 原生的版本化 JSON 模板，步骤模型更规整，支持条件与循环。

两者都是声明式 JSON，不执行 Python 或任意代码。这是 qdrust 与旧 QD 最重要的安全边界：模板描述「发什么请求、怎么判定、提取什么」，而不是一段可执行的程序。

旧 QD HAR

一个 HAR 模板是标准的 HAR 结构，额外的规则挂在每个 entry 上： 

{
  "log": {
    "entries": [
      {
        "request": {
          "method": "POST",
          "url": "https://example.com/api/checkin",
          "headers": [...],
          "postData": { "mimeType": "application/json", "text": "{\"sig\":\"{{sig}}\"}" }
        },
        "success_asserts":   [{ "re": "签到成功", "from": "content" }],
        "failed_asserts":    [{ "re": "已签到", "from": "content" }],
        "extract_variables": [{ "name": "token", "re": "token=(.+)", "from": "content" }]
      }
    ]
  }
}

三类规则

字段作用说明
extract_variables 提取变量 用 re 正则从响应中抽取，命名后供后续步骤以 {{name}} 引用。re 是对整个返回体文本做匹配。
success_asserts 成功断言 命中任一规则即判定该步骤成功。
failed_asserts 失败断言 命中任一规则即判定该步骤失败，优先于成功断言。

from 可选三个取值：content（响应体）、status（HTTP 状态码）、header（响应头）。 其中 re 按 Python 的读法解析——写法、flags、返回形状与边界见正则：按 Python 的读法解析。

导入与校验

在 WebUI 的模板页点击导入，选择从旧 QD 导出的 *.har.json 即可； 模板页也可以从订阅的模板库里挑模板——那条路是先预览、保存才入库。 本地文件同样可以用命令行先校验： 

cargo run -p qdrust-cli -- validate ./template.har.json

# 执行 HAR，传入变量与整体超时
cargo run -p qdrust-cli -- run ./template.har.json --var token=abc --timeout 60
CLI 的网络策略更严格

CLI 默认拒绝私网地址、localhost 与无效 TLS 证书，不像旧 QD 那样宽松。如果你在调试本机服务时被拒绝，这是刻意行为。服务端同样有闸门——默认只请求公网地址，指向内网 / 使用自签证书需管理员开启对应的高风险开关（见使用指南 · 出站请求与网络开关）。

保存前先「测试」一遍

新建 / 编辑任务弹窗里的「测试」会立刻用当前变量跑一遍模板。它走调度器同一条执行路径与出站闸门（同一套限制与政策）， 但不创建任务、不落运行记录，返回逐步结果与模板日志（POST /api/v1/templates/{id}/test）。断言和变量都确认无误再保存。

Template Schema v1

qdrust 原生模板要求顶层包含 version: 1、非空 name 和 steps：

{
  "version": 1,
  "name": "Health check",
  "variables": { "base_url": "https://example.com" },
  "steps": [
    {
      "type": "request",
      "name": "Fetch health",
      "method": "GET",
      "url": "{{base_url}}/health",
      "headers": { "accept": "application/json" }
    },
    {
      "type": "extract",
      "name": "Read status",
      "source": "status",
      "selector": "",
      "target": "status",
      "required": true
    }
  ]
}

步骤类型共五种：request、extract、if、for_each、delay；请求 body 支持 json、text 与 form。

硬性限制：最多 1000 个静态步骤、最多 16 层嵌套、单次 delay 最长 5 分钟。运行时还会独立限制请求数、循环次数、响应体大小与总时长——防止一个写错的模板把服务拖垮。

变量

变量有三个来源，按优先级覆盖：

  1. 创建任务时预填：模板里 {{name|default("...")}} 的字面量首参会作为默认值预填，用户改动优先。
  2. 运行期提取：由 extract_variables 在步骤执行后写入，供后续步骤引用。
  3. CLI 传入：--var key=value。

变量的引用语法是 {{name}}，求值发生在请求发送之前，且可以嵌套表达式（见下节）。注意执行是顺序的——在某一步里引用后面才提取的变量只会拿到空值。

模板变量是怎么算出来的

基于模板新建任务时，WebUI 需要知道「该让你填哪些变量」。这份清单由服务端按旧 QD HARSave.get_variables 的语义推导，通过 GET /api/v1/templates 的 variables 字段返回：

  • 只看请求实际读取的名字：method、URL、请求体，以及每个请求头 / Cookie 的名字与值；
  • 用 Jinja 解析，所以过滤器和函数名不算变量：{{jpop_username|urlencode}} 只产出 jpop_username，{{md5(password)}} 只产出 password；
  • 按条目顺序判定：只有被 extract_variables 提取之后的引用才不算输入。所以登录后的 {{token}} 不会被问，而先喂给 api://util/gb2312 再由该条目回写提取的 {{username}} 仍然是输入；
  • 无法解析的片段（如 {% while ... %} 控制条目）不产生变量。

默认值：{{name|default("...")}} 里的字面量首参会被提为默认值（variable_defaults 字段）， 新建任务时直接预填、用户改动优先。与 QD HARSave.post 的 init_env 一致：只认裸变量 + 字面量，首次声明为准， 非字面量（如 default(other)）不算。

native_v1 模板则直接用定义里声明的变量名（默认值取 variables 里声明的值）。

单模板代理（_proxy）

模板里写 {{_proxy|default("")}} 时，_proxy 会作为一个普通输入变量列出（默认空）。填了非空值后，这次运行的 每个请求都走该代理（http / https / socks5），用于过 CF 盾（trawl / flaresolverr）这类场景， 语义与 QD libs/fetcher.py::do_fetch 一致；留空即不走代理。

代理地址本身也要过同一道出站闸门：指向内网 / 回环（例如容器内的 http://flaresolverr:8191）时默认会被拒， 需要在管理页开启允许出站请求访问内网地址。这是刻意的——否则 _proxy 就成了绕过 SSRF 开关的后门。 代理无效时会明确报错，而不是静默直连。

表达式

模板变量与步骤请求支持 Jinja2 语法，由 minijinja 驱动。qdrust 注册了 54 个全局函数与 76 个过滤器（不含 __ 开头的引擎内部辅助项）。

其中 43 个（下表中带 ● 标记）同时注册为函数和过滤器。这复刻了 QD 的行为：QD 把 jinja_globals 同时写进 globals 和 filters，所以 {{ password|md5 }} 与 {{ md5(password) }} 两种写法都成立。

Python 写法：方法、% 格式化与列表就地修改

QD 模板是 Python，qdrust 在渲染前把这些写法改写成等价的引擎调用，模板可原样迁移：

写法说明
s.strip() / s.split(',') / s.replace(a, b) / s.upper() / s.startswith(x) / s.format(a, b)常用 str 方法；startswith / endswith 支持元组参数，find / index / count 支持起止下标，split 的 maxsplit、rsplit、splitlines 同样可用
d.get('k', '默认') / d.keys() / d.values() / d.items()字典读取；{% for k, v in d.items() %} 直接可用
items.index(x) / items.count(x)列表读取
"%s-%s" % (a, b) / "%d 分" % nprintf 风格格式化：%s / %r / %d / %f / %e / %g / %x / %o / %c / %%，以及宽度、精度与 - / 0 标志

改写只发生在 {{ … }} / {% … %} 内部，模板里的 HTML / JS 文本一字不动；不在支持列表里的方法名不做改写，照旧报 has no method named …，不会静默变成一次字典取值。

列表的就地修改

minijinja 的值默认不可变，而 Python QD 的 Jinja2 直接操作 Python 对象。不过 qdrust 对最常见的 模板自建累加器写法做了兼容：只要列表是在模板里用 {% set items = [] %}（或种子字面量 {% set items = ['a'] %}）声明的，.append / .extend / .insert / .pop / .remove / .clear 都可以直接用，无需任何改写： 

{# 模板自建的列表：qdrust 与 Python QD 行为一致 #}
{% set parts = [] %}
{% for x in rows %}{% set _ = parts.append(x) %}{% endfor %}
{{ parts | join('; ') }}

实现上，渲染前会把模板内的字面量列表声明替换为内部可变对象（引擎全局函数，不会出现在任务的必需变量列表里）；该改写只在模板中出现了就地修改调用时发生。仍然不支持的两类写法：

  • 对外部传入的变量（提取到的数组、函数返回值）就地修改——它们是共享的不可变值。改用 namespace 模式即可，改写后的模板在 Python QD 中同样合法，两边通用： 
    {% set ns = namespace(items=[]) %}
{% for x in rows %}{% set ns.items = ns.items + [x] %}{% endfor %}
{{ ns.items | join(',') }}
  • 字典的就地修改（.update 等）；拼接（+）、过滤（| select / | map / | sort）等纯函数写法不受影响。

正则：按 Python 的读法解析

success_asserts / failed_asserts / extract_variables 的 re 字段按旧 QD （libs/fetcher.py 的 run_rule）的读法解析：

  • 两种写法：裸模式（\d+）与斜杠形式（/(\d+)/g）。flags 只认 g/i/m/s/u——x 不在其中，所以 /(\d+)/x 是字面量模式而非斜杠形式；解析不出 flags 也不算错误，只是「没有 flags 的模式」。
  • g 是 QD 自己的开关，不是引擎 flag：有它走 findall，没有走 search。返回形状跟着捕获组数走——0 组给整段匹配、1 组给该组、多组给「每组一个」的元组（未参与匹配的组是空串），一条都没匹配给空列表。
  • 非 g：有组取第 1 组，无组取整段匹配。旧 QD 在第一组未参与匹配时会把 Python 的 None 存进变量（渲染成文本 "None"），这里改为回退到整段匹配。
  • u 是 Python 的默认值：Python 3 里 re.U 是 no-op，\w / \d / \b 一律按 Unicode 解释，与 u 无关。
  • 断言不读 flags：旧 QD 把断言的 re 原样交给 re.search，斜杠形式在那里只可能匹配它自己；这里对断言也按上面的规则解析——是超集，不是差异。

编译前会按 Python 的读法改写 pattern，抹平六处方言差异：

  1. 省略的重复下界：Python 的 {,n} 是 {0,n}、{,} 是 {0,}。
  2. 不成形的 {…} 当字面量：Python 只在后面跟成形重复时才把 { 当量词，所以 {"total":(\d+) 这类从 JSON 取值的写法在 QD 里正常，Rust 却会拒绝整个模式——把这类 { 转义成 \{。
  3. \Z 改写为 Rust 的 \z，两者都是「字符串末尾」。
  4. 反斜杠 + 标点还原成标点本身（Python 里 \< 就是 <，而 Rust 引擎拒绝这种转义、回溯引擎还会读成 Oniguruma 的「词首」）。
  5. 类内的 [ 转义为 \[：Python 没有 POSIX 类，[[:alpha:]] 是一串字符而非「字母类」——Rust 会把它读成 POSIX 类，编译通过却匹配错文本，最安静的一种差异。
  6. 反斜杠 + 数字：按 Python 的规则区分八进制转义与反向引用（例如 \0377 是 \x1f 加一个字面 7），改写成等值的 \xNN。

刻意拒绝的写法（翻译只能靠猜，猜错会匹配到错的文本，所以宁可报错）：{m,n} 里 m > n、 \N{...} 命名字符、(?a) ASCII 内联 flag；反向还有 (?<name>…) 这类 PCRE 具名组、(*FAIL) 这类回溯动词、 (?-i) 这种「组外关 flag」——它们能在这跑、在 Python QD 反而报错。已支持的包括 lookaround（(?= (?! (?<= (?<!）、 反向引用（\1）、八进制转义与条件组 (?(id)yes|no)。

两个引擎：线性引擎（regex，任何 pattern 都拖不进指数时间）先编，它拒了才用回溯引擎（fancy-regex）， 因为 Python 的 lookaround 与反向引用线性引擎没有。回溯引擎带固定上限（1000000 步），超限报错而不是当作「不匹配」； 并开了 seek 预过滤，避免「在每个位置都重扫一遍响应体」——没有它，一条断言对 100 KB 响应体要 63.8 秒才回「不匹配」。 仓库里 387 个模板共 6182 条 re，6181 条可编译，余下 1 条是模板自身的笔误（[^] 未闭合字符集，Python 同样拒绝），不是差异。

响应体编码

QD 模板的正则都写在中文页面上，读错编码就等于读错文本，所以响应体的解码顺序和 QD 的 utils.decode 一致：

  1. 响应头 Content-Type 声明的 charset。其中 ISO-8859-1 视为未声明——那是 HTTP 栈在没人决定时写的默认值，QD 也把它丢掉；
  2. 页面自带的 <meta charset=…> / <meta content="…;charset=…"> / <?xml … encoding=…?>；
  3. 都不说时按内容自动探测；
  4. 最后兜底 Latin-1。

gb2312 一律按 gb18030 解码（站点声明的窄集，字节里往往有超出 1980 字符集的字），无法解码的字节变成 U+FFFD 而不是让步骤失败。 from=content 的断言与提取读到的就是这段文本；响应的 content-type 是图片时，content 是原始字节的 base64 （QD getdata 的行为），验证码 / 图形接口这类步骤因此能直接把图取出来。

api://util/* 内置工具

当步骤 URL 以 api:// 开头时，executor 在进程内计算并返回结果，不发起真实 HTTP 请求。这意味着「取时间戳」「算个签名哈希」这类步骤零网络开销、无出站风险。

工具说明
delay固定 / 随机延迟（?seconds=N，或 QD 路径式 api://util/delay/N），响应文本与 QD 一致：delay N second.
timestamp?ts=<秒> 或 ?dt=<时间>&form=<strftime 格式>（都不给则用当前时间），返回 QD 同款中文键 JSON：完整时间戳 / 时间戳 / 16位时间戳 / 周 / 日 / 北京时间 / GMT格式 / ISO格式 / 状态
unicode / urlencode / urldecode编码转换
gb2312GB2312 百分号编码（urllib.quote 语义）
base64Base64 编码 / 解码
hashmd5 / sha1 / sha256 / sha512
totpTOTP（RFC 6238）：?secret=<base32>&digits=6&period=30&algo=sha1。在本地算码，2FA 密钥不出网；表达式侧同样可用 {{ totp(secret) }}（secret 会被识别为输入变量）
uuid / random随机值（UUID / 浮点数）

dddd/*OCR / 验证码识别，转发到外部 DdddOCR 服务（目标由 _server 参数或 QDRUST_DDDDOCR_SERVER 指定）。这是唯一会出网的 util 动作，因此和模板请求走同一道闸门：默认拒绝内网 / 回环地址

这套工具已与 QD 的核心语义对齐。旧 QD 的 toolbox 与 notepad 属于 Web 工具箱页面，不在模板 API 范围内，qdrust 未移植。 dddd/* 是其中唯一会出网的动作（转发到外部 DdddOCR 服务），因此和模板请求走同一道出站闸门，指向内网 / 本机自建服务时需要开启 允许出站请求访问内网地址。

外部插件二进制

除了内置的 util 与 browser，qdrust 还支持外挂插件二进制：通过子进程 JSON 协议调用，需带 manifest、通过 API 版本校验，并声明所需能力（network / read_file / write_file / environment）。WebUI 提供插件管理页。

能力声明是可审计的边界——一个声明了 network 的插件和不声明的插件，在 review 时是两个风险等级。
