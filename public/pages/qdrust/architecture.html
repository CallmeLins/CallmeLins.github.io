架构设计

运行时模型、执行链路、调度与租约队列、数据模型、安全边界与 API 全景。

工作区结构

整个项目是一个 Cargo workspace（resolver 3，Rust 2024 edition），默认成员是 qdrust-server：

qdrust/
├── crates/
│   ├── qdrust-core/            # HAR 解析、编译、变量求值、HTTP 执行
│   ├── qdrust-cli/             # 命令行校验与执行
│   ├── qdrust-server/          # Axum API、认证、调度、运行管理
│   └── qdrust-plugin-browser/  # chromiumoxide 无头浏览器插件
├── webui/                      # Vue 3 + TypeScript + Vite
├── migrations/                 # SQLite 迁移
├── migrations-mysql/           # MySQL 迁移
├── docs/                       # OpenAPI、模板 schema、各阶段设计文档
└── tests/fixtures/             # 旧 QD HAR 兼容样本

依赖方向是单向的：server 与 cli 都依赖 core，而 core 不依赖任何服务端概念。这意味着「解析并执行一个 HAR」这件事可以脱离 Web 服务独立存在——CLI 就是这条路线的产物。

运行时模型

qdrust 采用单进程 Tokio 异步模型（axum::serve），而不是 QD 的 Tornado 多进程模型。这个选择带来几个直接后果：

  • 横向扩展靠副本而非进程数：docker compose up --scale qdrust=N 加反向代理，而不是在单容器内 fork worker。
  • 进程内共享状态：无头浏览器客户端（chromiumoxide）在 server 进程启动时创建一次并全局共享。DOM 状态因此可以在多次独立调用间存活，这是实现「多步页面交互 / 人工过验证码后继续」的前提。代价是进程重启即清空会话。
  • 热重载与热更新：开发期用 cargo watch -x run；生产期由 QDRUST_CONFIG_FILE 与站点设置（admin API）提供运行时配置热更新，无需重启进程。

一次运行的执行链路

从调度器到 HTTP 请求落地，链路大致如下：

scheduler (SCHEDULER_INTERVAL_SECONDS，默认 15s)
   │  轮询到期任务
   ▼
run queue  ── claim_run / 租约 ──▶  运行记录 (runs + run_steps)
   │
   ▼
executor ──▶ 渲染变量 (minijinja) ──▶ fetcher
   │                                    │
   │                                    ├── 普通 HTTP 请求
   │                                    └── api:// 伪协议
   │                                          ├── api://util/*      进程内计算
   │                                          └── api://browser/*   远程 CDP
   ▼
extract_variables → 写入变量表 → 供后续步骤 {{var}} 引用
   ▼
success_asserts / failed_asserts → 判定成败
   ▼
通知渠道投递（10 种）· WebSocket 实时步骤流 · 运行日志

关键点在于 api:// 伪协议：当步骤 URL 以 api:// 开头时，executor 不会发起真实 HTTP 请求，而是在进程内计算结果（util）或驱动浏览器（browser）。因此「取个时间戳」「算个 MD5」这类步骤不需要任何外部服务，也不产生网络出站。

调度与运行队列

调度器按 SCHEDULER_INTERVAL_SECONDS（默认 15 秒）轮询到期任务，因此触发精度受该间隔影响——需要更精确就调小这个值，代价是更频繁的数据库轮询。

运行队列是非持久化本地队列，基于 SQLite 事务实现：

  • claim_run 以事务方式领取一条待执行运行，保证单实例下不会被重复领取；
  • 配合租约（lease）机制，实例崩溃或重启后未完成的运行会被重新认领，不会永久卡死；
  • 多实例共享同一个数据库时，同样由租约机制保证同一条运行不会被两个实例同时执行。
随机延迟

可视化调度器支持「随机延迟」，让同一任务的多次执行在时间上打散，避免被目标站点识别为固定节奏。对于签到类任务，这是一个实用而非装饰性的功能。

SQLite 与 MySQL 共用同一套实体定义，迁移脚本分别在 migrations/ 与 migrations-mysql/，切换只取决于 DATABASE_URL 的 scheme。

安全模型

  • 认证：本地为开放注册、bootstrap 初始管理员、忘记/重置密码、可选邮箱验证（REQUIRE_EMAIL_VERIFICATION）；登录有独立限流（默认 5 次 / 60 秒）。自托管还可叠加外部身份提供方（OIDC 授权码 + PKCE，或反向代理 Header 认证），本地账号密码能力始终保留，详见使用指南 · 第三方登录。
  • 会话：SESSION_TTL_SECONDS 默认 7 天；CSRF 令牌轮换；HTTPS 下必须开启 COOKIE_SECURE。可选 Redis 会话缓存（仅加速，非必需）。
  • 归属校验：所有用户资源（模板、任务、运行、通知渠道）均在服务端执行归属校验，而不是依赖前端过滤。
  • SSRF 防护：CLI 默认拒绝私网地址、localhost 与无效 TLS 证书——这是刻意区别于旧 QD 宽松策略的一点。服务端执行不受此限制。
  • 模板沙箱：模板是声明式 JSON，不执行 Python 或任意代码。Template Schema v1 限制最多 1000 个静态步骤、16 层嵌套、单次 delay 最长 5 分钟；运行时另外限制请求数、循环次数、响应体大小与总时长。
  • 插件能力声明：外部插件二进制需带 manifest，声明 network / read_file / write_file / environment 能力并做 API 版本校验，通过子进程 JSON 协议调用。

API 一览

所有业务接口位于 /api/v1 下，完整契约见仓库内的 docs/openapi-v1.json 与运行时的 /api/v1/openapi.json。

分组端点
运维GET /health · GET /ready · GET /api/v1/openapi.json
认证/api/v1/auth/bootstrap · /login · /logout · /register · /session
模板/api/v1/templates · /{id} · /import-qd-har · /validate-qd-har · /{id}/publish · /{id}/qd-har
任务/api/v1/tasks · /tasks/batch · /task-groups · /tasks/{id}/run
运行/api/v1/runs · /{id} · /{id}/cancel · /{id}/steps · /{id}/steps/live（WebSocket）
管理员/api/v1/admin/users · /settings · /backup · /restore · /push-requests
生态/api/v1/plugins · /api/v1/public-templates

可观测性与运维端点

  • 步骤级回放：每次运行按步骤记录请求、响应与提取到的变量，可在运行记录里逐步查看。
  • QD 风格运行日志：文本化日志，便于直接阅读与检索。
  • WebSocket 实时流：/api/v1/runs/{id}/steps/live 推送活跃运行的步骤；订阅导入进度同样走 WebSocket。
  • 探针：/health 与 /ready 供 Compose 健康检查与反向代理使用。
  • 日志保留：LOG_RETENTION_DAYS（默认 0 永久保留）控制已完成运行记录的自动清理，系统每小时执行一次。

横向扩展的边界

单进程模型不意味着只能单实例。多实例共享同一数据库时，运行队列的租约机制保证不重复执行；会话可由可选的 Redis 缓存加速。推荐形态是 Docker 副本 + 反向代理。

但有两处状态是进程内、不跨实例共享的，扩展时需要留意：无头浏览器会话（存在 server 内存中）与运行时热更新配置（各实例需各自加载同一份 QDRUST_CONFIG_FILE）。
